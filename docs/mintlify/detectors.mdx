Fixor ships four detectors today. All four run on every scan
unless you've narrowed the allowlist in your org settings. Each
one is implemented as a `Detector` class in
[`src/analysis-engine/detectors/`](https://github.com/tornidomaroc-web/fixor/tree/main/src/analysis-engine/detectors)
— readable in ~200 lines per family.

## SQL injection

<Info>Detector id: `sql-injection-js-ts`</Info>

What we look for:

- String concatenation or template-literal interpolation into
  query builder methods (`db.query(...)`, `connection.execute(...)`,
  Knex's `.raw()`, raw `mysql2`/`pg` calls).
- Drivers covered by the rewrite engine: **MySQL2**, **node-postgres
  (`pg`)**, **Knex**, **Prisma raw queries**.
- Common false-positive guards: a query with no user-controlled
  inputs (literal strings, env vars) is not flagged.

Fix shape:

```js
// Before
db.query(`SELECT * FROM users WHERE id = ${req.params.id}`)

// Fixor's suggested fix
db.query("SELECT * FROM users WHERE id = ?", [req.params.id])
```

## Cross-site scripting (XSS)

<Info>Detector id: `xss-js-ts`</Info>

What we look for:

- DOM sinks where untrusted data lands without escaping:
  `element.innerHTML = …`, `document.write(…)`, `eval()`,
  `outerHTML`, `insertAdjacentHTML`.
- React-specific bypass patterns (`dangerouslySetInnerHTML`,
  unescaped raw HTML in `useEffect` handlers).
- Server-side template sinks where applicable (Express
  `res.send` of user input without escaping).

Fix shape:

```js
// Before
container.innerHTML = `<h1>Hello, ${name}</h1>`

// Fixor's suggested fix
container.textContent = ""
const h1 = document.createElement("h1")
h1.textContent = `Hello, ${name}`
container.appendChild(h1)
```

## Command injection

<Info>Detector id: `command-injection-js-ts`</Info>

What we look for:

- `child_process.exec` or `execSync` with user-controlled string
  concatenation (the family of bugs that yields RCE).
- `child_process.spawn` / `spawnSync` where the **command itself**
  is user-controlled, even if args are an array.
- Shell-interpolation patterns: `` `cmd ${userInput}` ``.

Fix shape:

```js
// Before
exec(`git log --author=${author}`, (err, stdout) => { ... })

// Fixor's suggested fix
import { execFile } from "node:child_process"
execFile("git", ["log", "--author", author], (err, stdout) => { ... })
```

## Path traversal

<Info>Detector id: `path-traversal-js-ts`</Info>

What we look for:

- File API arguments (`fs.readFile`, `fs.createReadStream`,
  `fs.writeFile`, `path.join`, `express.static`) where the path is
  derived from request input.
- `..` traversal patterns the analysis engine can prove are
  reachable from request data flow.
- Missing allowlist / `path.resolve` + prefix-check patterns.

Fix shape:

```js
// Before
res.sendFile(`/var/data/${req.params.filename}`)

// Fixor's suggested fix
import { resolve, sep } from "node:path"
const root = resolve("/var/data")
const target = resolve(root, req.params.filename)
if (!target.startsWith(root + sep)) return res.sendStatus(400)
res.sendFile(target)
```

## What about false positives?

Fixor's analysis is performed by Claude — it reasons about your
specific code, not just patterns, so the false-positive rate is
materially lower than regex-based scanners. That said, every
finding is a *suggestion*. You're the reviewer.

If a particular finding is wrong for your codebase, tightening the
**severity threshold** or adding the file's path to **ignored
globs** in your org settings stops Fixor from raising it on
subsequent scans without disabling the whole detector.
