title: "Detector catalogue"
description: "What each of Fixor's six detector families flags, the patterns they cover, and what they explicitly do not claim."
---

Fixor ships six detector families. All six run on every scan unless
you have narrowed the allowlist in your org settings. Each detector
is implemented as a `Detector` class under
[`src/analysis-engine/detectors/`](https://github.com/tornidomaroc-web/fixor/tree/main/src/analysis-engine/detectors)
and is gated by a regex prefilter before any LLM call, so a file
that contains none of the detector's sentinel patterns is dropped
without spending a token.

The authoritative scope contract for what each detector catches and
explicitly does not catch lives at
[`docs/detector-capabilities.md`](https://github.com/tornidomaroc-web/fixor/blob/main/docs/detector-capabilities.md).
This page summarizes; that file wins on any conflict.

## Authentication bypass

<Info>Detector id: `auth-bypass-multi`</Info>

What we look for:

- **Sentinel-string bypasses** in TypeScript, JavaScript, Python, Go,
  and Ruby: hardcoded `"anonymous"` / `"admin"` / `"public"` defaults,
  `|| true` short-circuits, `|| "admin"` and `?? "admin"` fallbacks,
  JWT verification swallowed inside try/catch, Python
  `verify_signature=False`, `DEFAULT_USER_ID` / `DEFAULT_ADMIN_ID` /
  `DEFAULT_ADMIN_EMAIL` fallbacks, Ruby `params[:x] || "admin"`.
- **Missing-middleware bypasses** on router-style frameworks: a
  destructive route declaration with no authentication middleware in
  the argument list, where sibling routes on the same router do pass
  an auth middleware. **Express-family by fixture coverage**;
  **router-style identifier syntax by regex** — the regex matches
  literal `router` / `app` / `api` identifiers, or any identifier
  ending in `Router` / `App` / `Api` (so `adminRouter.post(...)` is
  covered). Verbs covered: `get`, `post`, `put`, `delete`, `patch`,
  `use`, `all`. Fastify, Koa, or Hono callsites whose identifiers
  also match the regex shape reach the LLM stage and are judged on
  the same missing-auth-arg criteria, but they have no positive
  fixture coverage and are not baseline-anchored.

Explicitly not covered (escalate to a manual review):
Fastify, Koa, Hono, NestJS Guards, Spring `@PreAuthorize`, ASP.NET
`[Authorize]`, GraphQL resolver-level auth, declarative Rails route
guards, tRPC `protectedProcedure`, Next.js middleware-based auth.

Next.js App Router method-named exports (`export const POST = ...` /
`export async function GET(...)`) ARE now covered via missing-HOC-
wrapper detection. Measured 2026-05-23 against 182 of 228 inbox-zero
App Router routes (~80%, PARTIAL scan, halted for API budget — not a
full-corpus sweep): 0 auth-bypass findings on the partial 182-route
sample, including all measured `withAuth` / `withAdmin` / `withEmailAccount`
/ `withEmailProvider` / `withError` wrapper shapes. The body-
discriminator rule generalized correctly to unfamiliar ApiKey-suffix
wrappers in Phase D synthetic measurement (`withAccountApiKey`,
`withStatsApiKey`); unfamiliar wrappers with no body enforcement
surface at MEDIUM in the review queue, not as HIGH alerts in the
main panel.

Remix v2 `loader` / `action` exports ARE now covered (Phase E,
2026-05-23): a sibling `REMIX_HANDLER_DEF_RE` matches
`export const loader = ...` / `export const action = ...` shapes and
routes the file to the same missing-HOC-wrapper rubric as App Router.
A path-aware filter bounds over-match to the Remix v2 file-system
convention (`/routes/` segment or `app/root.{ts,tsx}`) so utility
modules under `app/lib/` or `app/utils/` that happen to export
`loader` / `action` factory functions are not misrouted to the LLM.
**Synthetic calibration: 6 Remix fixtures (3 positive + 3 negative,
including the over-match utility anchor) all 6/6 passed. End-to-end
demo: fixor-demo-remix planted-vuln scan flagged the planted
auth-bypass on `app/routes/admin.users.$id.delete.ts` with reasoning
that explicitly named "Remix `action` export" — the SYSTEM_PROMPT
case 3 framing generalized to Remix shape without prompt changes.**
**Named residuals at the point of this claim:** (i) the real-world
production-corpus baseline against a Remix codebase (e.g.
Trigger.dev's 411 routes) is **deferred** — it would bound the
HOC-name-divergence class on one corpus but does not eliminate it,
and the cheap calibration + demo were deemed scientifically
sufficient under the Phase D partial-sample discipline; (ii)
**non-conventional wrapper-name divergence on unknown Remix
codebases is a known residual** until a real corpus is measured —
calibration covers `withAuth`, `withAdmin`, `withLogging`,
`withSessionAnalytics`, `requireUser`, `getServerSession`, but a
customer codebase using a deceptive non-conventional wrapper name
could surface a false positive. The path-aware filter **bounds, not
eliminates**, the divergence class. **Customer wrappers whose name
suggests auth but whose implementation is a no-op stub** (e.g. a
`withAuth` defined as `(fn) => fn` in a sibling file) are also out
of scope — Fixor reads the route file in isolation and trusts the
auth-suggesting name; to verify, audit the wrapper's implementation
in its defining file.

The sentinel-string sub-claim is content-based and still fires on
both router-style and file-system-routed (App Router, Remix) files
normally.

**Cross-file parent-layout guard recognition (Remix / React Router
v7, Phase G 2026-05-28).** A route whose auth gate lives in an
ancestor `_layout.tsx` loader (the standard Remix flat-routes
pattern) is recognized as gated for READ (loader) concerns, so the
cross-file false positive is suppressed. Suppression is conservative
by construction: it requires (a) a layout loader that BLOCKS on
failure (throw redirect / 401 / 403 — a non-blocking session read is
not a gate) and (b) STRUCTURALLY PROVEN coverage via unbroken
`+`-folder nesting with no trailing-underscore opt-out. Coverage that
cannot be proven is dropped (the route flags at its natural severity),
never suppressed; and a destructive `action` is NEVER cleared by a
parent layout loader (in the Remix/RR v7 lifecycle an action runs
before parent loaders). **Layout-level auth is recognized for Remix
and React Router v7 only; App Router cross-file auth (middleware
matchers, `layout.tsx` / DAL gating) remains a named limitation,
addressed in a later phase** — an App Router `layout.tsx` does not
wrap Route Handlers and Next.js discourages layout-based authz, so
its coverage is not structurally provable. Validated on the real
Documenso clone (3/3 admin read routes: false positive before,
cleared after); coverage proof unit-tested 7/7, suppression and
adversarial verdicts gated 6/6.

## Missing admin checks

<Info>Detector id: `admin-check-multi`</Info>

What we look for:

- **Hardcoded-admin shapes** in TypeScript, JavaScript, Python, Go:
  `email === "x@y.z"`, `email.endsWith("@domain")`,
  `email.includes("admin"|"owner"|"founder"|"root"|"superuser")`, Go
  `strings.HasSuffix(email, "@x")`, `ADMIN_EMAIL` / `admin_email`
  constants, `ADMIN_EMAILS` / `admin_emails` allowlist arrays,
  `DEFAULT_ADMIN_ID`, `DEFAULT_ADMIN_EMAIL`, `role || "admin"`,
  `role ?? "admin"`, `req.body|query|params.<role>` reads,
  `role === "admin"` string compare on a client-controlled value.
- **Missing-admin-gate shapes** on router-style frameworks: a
  privileged route (role or tier change, user management, billing
  settings, `/admin/*` paths) with no admin authorization check in
  either the middleware list (`requireAdmin`, `isAdmin`, `adminOnly`,
  `verifyAdmin`) or the handler body, where sibling routes on the
  same router are admin-gated. Same regex-vs-fixture asymmetry as
  missing-middleware bypasses above: **Express-family by fixture
  coverage; router-style identifier syntax by regex.** Fastify, Koa,
  or Hono callsites whose identifiers match the regex reach the LLM
  and are judged on the same missing-admin-gate criteria, but have
  no positive fixture coverage.

Explicitly not covered: Fastify, Koa, Hono, NestJS Guards, Spring
`@PreAuthorize`, decorator-based RBAC, declarative RBAC (Casbin, OPA,
Cedar), tRPC `adminProcedure`, GraphQL resolver-level admin checks.

Next.js App Router method-named exports ARE now covered via missing-
admin-HOC-wrapper detection. Phase C calibration on 4 positive + 4
negative synthetic fixtures with a helper-call symmetric anchor (AC-
P4 / AC-N4); Phase D real-world partial scan on 182 of 228 inbox-zero
App Router routes (~80%, PARTIAL scan, halted for API budget — not a
full-corpus sweep) returned 0 admin-check findings on the partial
182-route sample, including the corpus's `admin/*` routes.

Remix v2 `loader` / `action` exports ARE now covered (Phase E,
2026-05-23) via the sibling `REMIX_HANDLER_DEF_RE` and the
`isRemixRoutePath` path-aware filter described in the auth-bypass
section above. Same calibration set (6 Remix fixtures, all 6/6
passed); demo-proven on a planted admin role-change at
`app/routes/admin.users.$id.role.ts` wrapped only in `withAuth`,
correctly identified as missing admin authorization. **Named
residuals at the point of this claim mirror the auth-bypass
section:** (i) **Trigger.dev real-world baseline is deferred** —
calibration + demo were sufficient under the Phase D partial-sample
discipline; (ii) **non-conventional admin-wrapper-name divergence on
unknown Remix codebases is a known residual** — the path-aware
filter bounds the over-match class but does not measure the universe
of HOC names Remix customers might use. **Admin-suggesting wrappers
whose body does not actually enforce admin** are out of scope — a
wrapper named `withAdmin`, `requireAdmin`, `withAdminLogging`,
`withAdminMetrics`, etc. whose body is a no-op stub (`(fn) => fn`)
or logging-only / metrics-only ships unguarded; Fixor trusts the
admin-suggesting name without reading the body. By design: corpus
grep across cal.com, documenso, convoform, grafana, and the Phase D
inbox-zero log found zero such non-enforcing `withAdmin*` wrappers
in real-world OSS, so the admin-substring rule stays untightened (in
contrast to auth-bypass's `session`-substring body-discriminator
clause, where the non-auth shape DOES appear in the wild). The
hardcoded-admin sub-claim is content-based and still fires on
router-style and file-system-routed (App Router, Remix) files
normally.

When auth-bypass and admin-check both fire on the same `file:line`,
the admin-check finding is dropped (the auth-bypass finding subsumes
it; "no auth at all" is strictly worse than "no admin gate" and the
remediation is the same).

## IDOR (insecure direct object reference)

<Info>Detector id: `idor-multi`</Info>

What we look for:

- A database read or write where a request-derived id
  (`req.params.id`, `req.body.id`, tRPC `input.id`, FastAPI path
  param, Rails `params[:id]`, Go chi `chi.URLParam`) flows into a
  query (`findUnique`, `findFirst`, `update`, `delete`, raw SQL,
  `pool.query`) with no ownership filter
  (`userId: ctx.session.user.id` or equivalent) in the `where` clause
  and no post-fetch ownership check.
- Router frameworks covered by fixtures: Express, Next.js app router,
  Fastify, Hono, tRPC, NestJS, FastAPI, Rails, Go chi with raw SQL.

Explicitly not covered: IDOR via predictable storage filenames (S3,
GCS), tenant-scoping bugs (`orgId` missing instead of `userId`),
GraphQL field-level IDOR, business-logic IDOR (e.g. changing another
user's email by knowing the email), TOCTOU race conditions on
ownership checks.

## Environment-variable exposure

<Info>Detector id: `env-exposure-multi`</Info>

What we look for:

- `process.env` serialized into an HTTP response body (Express
  `res.json(process.env)`, Fastify, Flask `jsonify`, FastAPI).
- `JSON.stringify(process.env)` reaching a logger payload.
- Go `os.Environ()` or `os.LookupEnv` echoed back in a handler
  response.
- Partial-redaction patterns where the allowlist has gaps.

Explicitly not covered: env vars leaking via error stack traces, env
vars in build-time bundles (Next.js `NEXT_PUBLIC_*` overlap is owned
by `secrets-exposure`), env vars leaked to third-party webhook
payloads, env vars logged at startup, env vars baked into Docker
image layers.

## Hardcoded secrets

<Info>Detector id: `secrets-exposure-multi`</Info>

What we look for:

- Literal API keys, tokens, and signing secrets: Stripe `sk_live_*`,
  OpenAI `sk-*`, Anthropic `sk-ant-api03-*`, AWS `AKIA[A-Z0-9]{16}`,
  Slack webhook URLs, Postgres passwords in connection strings,
  hardcoded JWT signing secrets in source.
- `NEXT_PUBLIC_*` env vars that expose server secrets to the client
  bundle.
- Supabase service-role key reaching client-side code.
- Firebase admin SDK credentials inside client components.

Explicitly not covered: secrets in git history (only the present tree
is scanned), secrets in built bundles after a build step, secrets in
`.env*` files (path-skipped) or test fixtures (path-skipped), secrets
stored in third-party config systems (Vault, AWS Secrets Manager) and
incorrectly retrieved, encryption-at-rest issues.

## Unverified webhook handlers

<Info>Detector id: `webhook-unverified-multi`</Info>

What we look for:

- Webhook handler routes (`/webhook`, `/hook`, `/hooks` URLs or
  handler functions named `*Webhook*`) in Express/Fastify-style
  routers, Flask decorators (`@bp.post`), Rails `post` routes, and Go
  `HandleFunc`.
- File-system-routed webhook handlers in Next.js App Router
  (`app/api/<provider>/webhook/route.ts`) and Remix v2
  (`app/routes/webhook.<provider>.ts` or `app/routes/api.webhook.*.ts`):
  the route-def prefilter routes the file to the LLM, which judges
  webhook-vs-not by file path segment, signature-header reads, and
  `node:crypto` HMAC operations. Remix coverage added Phase E
  (2026-05-23) with the same `isRemixRoutePath` filter bounding
  over-match to `/routes/`; calibration: 5 Remix webhook fixtures
  (2 positive Stripe-no-sig / GitHub-no-HMAC + 2 negative
  constructEvent / timingSafeEqual + 1 over-match utility), all 5/5
  passed. **Named residual: real-world Remix webhook baseline is
  deferred** — Trigger.dev-scale corpus verification would buffer the
  webhook-shape coverage class but is not blocking; the cheap
  calibration and the fixor-demo-remix end-to-end planted-vuln scan
  established the capability.
- No signature verification at all on a webhook handler.
- Explicit env-flag bypass of verification (e.g. `WEBHOOK_VERIFY=off`
  short-circuiting `constructEvent`).
- Raw string-compare of signatures (`sig != expected`, classified
  MEDIUM as a timing leak).

What we correctly skip (recognized as safe):
`stripe.webhooks.constructEvent` / `stripe.Webhook.construct_event`,
`@octokit/webhooks` + `createNodeMiddleware`,
`twilio.validateRequest`, `crypto.timingSafeEqual`, Python
`hmac.compare_digest`, Go `subtle.ConstantTimeCompare` and
`hmac.Equal`, and dedicated verification middleware mounted before
the handler.

Provider coverage by fixtures today: Stripe, GitHub, Twilio, Slack,
Lemon Squeezy, and custom HMAC.

Explicitly not covered: Shopify (`X-Shopify-Hmac-Sha256`), Discord
interactions (Ed25519), Mailgun, SendGrid, AWS SNS subscription
confirmation, GCP Pub/Sub push (OIDC token), Square, PayPal, Paddle,
Plaid, Algolia, Cloudflare Workers signed requests, replay-protection
issues independent of signature verification, key rotation, mTLS.

**Critical scope limitations** (four, in two classes — silent-skip prefilter
gaps and false-positive-shape limitations):

(a) **URL matched in file content, not file path.** Five of the
eleven prefilter patterns require the webhook URL to appear as a
string literal in file content alongside router-style syntax
(Express `app.post` / `router.use` + path, Flask decorator + path,
Rails `post` + path, Go `HandleFunc` + path). File-system-routed
frameworks (Next.js App Router, Remix) put routing in the file path
— e.g. `app/api/<provider>/webhook/route.ts` — so these patterns
never fire on those handlers. The Stripe-at-`POST /billing/events`
case is a second instance: when the URL string in content does not
carry the `webhook` / `hook` / `hooks` token, the URL-name patterns
silently skip even on Express.

(b) **Content prefilter is blind to DIY-HMAC handlers that are
silent.** A handler that imports no webhook library
(`@octokit/webhooks`, `stripe.webhooks.constructEvent`,
`twilio.validateRequest`, etc.) AND exhibits no signature-comparison
anti-pattern (no `sig != expected`, no `WEBHOOK_VERIFY=off`) is
invisible to the content prefilter. The inbox-zero Lemon Squeezy
handler at `apps/web/app/api/lemon-squeezy/webhook/route.ts` is
exactly this case: correct `crypto.timingSafeEqual` verification, no
webhook-lib import, no anti-pattern, so no prefilter pattern fires
and the file never reaches the LLM. The invisibility is because the
file is correct, not because all DIY-HMAC is inherently invisible —
a vulnerable DIY-HMAC handler that uses `sig != expected` would
still hit the looser-comparison content patterns.

(c) **Cross-file webhook verification helpers.** App Router webhook
routes that delegate verification to a helper imported from another
module — e.g. `await verifyAppleNotificationPayload(body.signedPayload)`
from `@/ee/billing/apple`. **Phase F + Path-A structural follow-up
(2026-05-23) lifted this from HIGH to MEDIUM/review-queue.** Phase F's
first cut handled the case where the verifier import path was
verification-suggesting (e.g., `@/utils/webhook/validate-webhook-
account`) or the helper call sat within the ±8/+16 line window the
webhook detector shipped around the route declaration. The structural
follow-up switched the webhook detector to whole-file payload for
App Router route-def triggers — matching the auth-bypass /
admin-check discipline already in place — which closed the window-
truncation residual Phase F's first cut left open. The LLM now sees
the awaited helper call wherever it sits in the route file. Measured
success on both real inbox-zero routes: Outlook webhook and Apple
App Store Server Notifications both correctly route to MEDIUM/review-
queue. The remaining bound is the 200KB whole-file cap (pathologically
large webhook handlers fall back to windowed payload) and non-App-
Router webhook triggers (express/flask/rails/go URL-name patterns
keep their existing windowed payload because their prefilter signals
are local). Audit the helper's implementation to confirm a MEDIUM
finding is a false positive in your codebase.

(d) **Non-HMAC shared-secret challenge verification.** Microsoft
Graph webhooks compare `notification.clientState` against an env-
stored expected value and return 403 on mismatch — that IS
verification, but it is shared-secret equality, not HMAC. **Phase
F (2026-05-23) lifted this from HIGH to MEDIUM/review-queue.** The
webhook prompt now recognizes the body-field-compare-against-env-
value-with-unauthorized-status shape as the documented Microsoft-
Graph subscription-validation pattern, routes it to MEDIUM (the env
value cannot be confirmed cross-file, which is why MEDIUM rather
than LOW), and the LLM reasoning explicitly names the field, env
value, and 403 response. Measured Phase F success: inbox-zero's
Outlook (Microsoft Graph) webhook handler correctly dropped to
MEDIUM/review-queue post-tune. Other shared-secret challenge
mechanisms (custom integrations, internal services) using the same
body-field-compare-env-and-unauthorized-on-mismatch shape route the
same way. Class (d) has no observed window-truncation residual in
the Phase F measurement: the compare happens close to the route
declaration in the outlook real-world case.

**MEDIUM-confidence findings on this detector** (timing-leak
comparisons, env-flag-conditional bypass) are routed to the internal
review queue, not posted as a PR-comment finding, matching the
HIGH-only emit policy used by the other five detectors.

## How findings are produced

Each detector follows the same two-stage pipeline:

1. **Regex prefilter:** sentinel strings plus (for `auth-bypass`,
   `admin-check`, `webhook-unverified`) route-definition patterns.
   Files with zero matches are dropped without an LLM call. This is
   what keeps a scan's cost bounded — typically about $0.012 per file
   for the base analyzer pass, plus roughly $0.036 extra per
   route-shape file (Next.js App Router HTTP-method exports or
   Express-family `router.METHOD(...)` declarations) where three
   additional detector passes run. The CLI prints a corpus-specific
   estimate before each scan, so you see the actual figure for your
   repo rather than a flat per-file number.
2. **LLM verdict:** for files that pass the prefilter, Claude reads
   the full file (for route-definition triggers) or a windowed
   context (for sentinel triggers) and produces a confidence-graded
   verdict. Only HIGH confidence verdicts surface as PR-comment
   findings; MEDIUM verdicts land in an internal review queue.

The driver of false-positive control is Claude reasoning per
finding, not a single tunable rate.

## What about false positives?

Every finding is a suggestion, not a guarantee. If a specific finding
is wrong for your codebase you have two settings-level escapes that
apply on the next scan, no redeploy needed:

- **Severity threshold:** drop low-severity findings before they
  reach the comment.
- **Ignored globs:** skip a path entirely (e.g. `vendor/**`,
  `**/*.test.ts`).

Neither disables a whole detector; both narrow noise. To turn off a
specific detector entirely, use the detector-allowlist mode on the
settings page.

## Roadmap

Vulnerability classes we are tracking but have not shipped:

- **CSRF / same-origin:** missing tokens, framework-specific bypass
  patterns.
- **SSRF:** outbound HTTP from user-controlled URLs.
- **Mass assignment:** Prisma / Drizzle / SQLAlchemy update bodies
  that accept fields a user should not be able to set.
- **Insecure deserialization:** `node-serialize`, custom shapes.

Detector demand drives the order: email
<a href="mailto:support@fixor.dev">support@fixor.dev</a> with the
class you want and the framework you ship.
