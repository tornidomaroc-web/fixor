LLM-based security tools can leak the secrets they detect

We found our own scanner quoting a secret it had just flagged into the comment it was about to post. The detector worked. The explanation was the leak. Here is what happened, why it is structural, and what we did about it.

The finding

Earlier this month, during an audit of our own detectors, we were running a routine stability test on Fixor, the pull-request review tool we build. Fixor scans the diff in a pull request for a small set of vulnerability classes and posts an explanation of each finding as a PR comment. The stability test runs each detector repeatedly against a set of test fixtures and records what it produces.

One of those fixtures is a Go file containing a hardcoded JWT signing key. The value is synthetic, a string we wrote for the fixture, not a real credential: 

const jwtSigningKey = "PROD-jwt-acme-9d8f7a6c5b4e3d2f1a0b9c8d7e6f5a4b"

Our secrets-exposure detector flagged it correctly. That was the expected result. What was not expected was the explanation text. The model we use to validate and describe findings had quoted the key, in full, into the reasoning it produced, and that reasoning was on its way into a PR comment. If this had been a real pull request on a real repository, the comment would have republished the secret to everyone with read access to that repository.

The detector did its job. It found a hardcoded secret. The problem was that the act of explaining the finding reproduced the thing the finding was about. The finding was the leak.

Why this is structural, not a bug

Our first instinct was that this was a defect in our prompt or our output formatting. It is not. It is a structural property of how this category of tool is built.

LLM-based security tools generally use a language model for one of two jobs: validating whether a regex or static-analysis hit is a true finding, and writing the human-readable explanation that goes to the developer. In both jobs the model is handed the code under review and asked to reason about it. Language models trained on code quote the code they reason about. That behavior is normal and usually helpful. When the code under review contains a secret, a credential, or another sensitive value, the model's reasoning quotes that value the same way it would quote any other token.

The tool then renders that reasoning into an output channel: a pull-request comment, a dashboard, a chat message, an email. Those channels have a wider audience than the source file did. A secret sitting in one file in a private repository is visible to the people who can read that file. The same secret quoted into a PR comment is visible to everyone with read access to the repository, and depending on configuration to notification emails and downstream integrations. The tool has moved sensitive content from a narrow surface to a wide one, through the model's output, and no person decided to do that.

Where this sits in the OWASP taxonomy

We think this belongs in the conversation around the OWASP Top 10 for LLM Applications. It reads as a concrete instance of LLM02, Sensitive Information Disclosure, with a strong overlap with LLM05, Improper Output Handling. LLM02 captures the disclosure itself: sensitive data reaches a party that should not see it. LLM05 captures the missing control: the application passes model output to a downstream channel without sanitizing it.

We are not arguing for where it should be placed. That is for the working group. We raise it because the case is specific to security tooling, where the model is deliberately pointed at the most sensitive code in a repository, and because we did not find it described in either entry's current public text. We notified the OWASP Gen AI Security Project about this before publishing, which we describe at the end of this post.

The same shape in another detector

The JWT key was the clearest case, but it was not the only one. When we audited our other detectors for the same property, our admin-check detector showed a related, lower-severity version of it.

admin-check looks for authorization decisions made against hardcoded identity values, for example an allowlist of email addresses treated as the set of administrators. The fixtures for that detector contain hardcoded email allowlists. They are synthetic addresses for a fictional company, values such as founder@acme.app and cto@acme.app that we wrote for the test set. The detector's model reasoning would quote those addresses when it explained a finding, the same way the secrets detector quoted the JWT key. In a real codebase those values would be real email addresses and real internal identifiers. We classified this as a medium-risk version of the same issue: the leaked content is identity data rather than a credential, but the mechanism, model reasoning quoting matched content into a wider channel, is identical.

What other tools document

We reviewed the public documentation, product pages, and white papers of six AI-augmented security products on 19 May 2026. The six were Snyk Code AI, GitHub Copilot Autofix, Semgrep Assistant, Endor Labs, Corgea BLAST, and Aikido. None documents an output-side mitigation for this disclosure class, meaning redacting secrets or source content from the model's output before it reaches a customer-visible channel. Several document input-side controls instead, such as minimizing the code sent to the model, anonymizing it, and not training on it. GitHub Copilot Autofix documents a filter for harmful suggestions. None of these addresses the output path: a model still receives the code and can quote a secret from it into a PR comment or dashboard. We are not claiming internal mitigations do not exist. We are reporting that the public surface is silent on the output path.

Our full review, with the URL and an exact quote for every product, is published as competitor-survey-2026-05-19.md in the Fixor repository, so the negative claim can be checked rather than taken on trust.

The mitigations, ranked by how much you can trust them

There are three ways to stop model reasoning from leaking matched content, and they are not equally trustworthy.

The strongest is to not generate the reasoning with a model at all for the affected findings. Replace it with hand-authored explanations. The explanation names the vulnerability class, the attack surface, and the remediation. It is written once, by a person, with no access to any specific matched value. Because the explanation never sees the source content, it cannot quote it. The property holds by construction, at authoring time, rather than depending on anything that happens at output time.

The middle option is a redaction layer applied to model output before it is emitted. Run the detector's own secret-matching patterns against the model's reasoning text and replace any match with a placeholder. This is worth having as defense in depth, because it catches cases the first option does not. It is weaker because it only catches secret shapes the detector already recognizes. A novel or unusually formatted secret that the model quotes can pass straight through it.

The weakest is a system-prompt instruction telling the model not to quote secret values. It relies on model compliance, which is probabilistic. It will work most of the time and fail some of the time, and the failures are exactly the high-severity cases. It should never be the only control. If it is used at all, it should be paired with the redaction layer.

What we shipped

We changed two detectors.

For secrets-exposure, we made the regex-only path the default. In that mode the detector matches its patterns, and when it finds a hardcoded secret it emits a hand-authored explanation for that pattern class. It makes no model call. The explanation describes the bug and the fix without echoing the matched value. The model-based mode still exists, but it is now opt-in behind an environment variable rather than the default. A detector that never sends the secret to a model, and never renders model reasoning, cannot leak through this path.

admin-check needed a more careful change, because not every one of its patterns can drop the model. We inventoried its twelve patterns and classified each into one of two tiers. Eleven are literal: the pattern match is itself the finding, and no surrounding context can make the match safe. For those, the model was only ever confirming what the regex had already proved, so we route them through hand-authored explanations, the same as secrets-exposure. One pattern is a judgment pattern. It matches a shape that can be either a real bug or safe code depending on context, and separating the two genuinely needs the model to read the surrounding data flow. That one pattern keeps the model. We did not apply a blanket bypass, because bypassing the model on the judgment pattern would have turned safe code into false positives. The tier classification lives in the detector source as a field on each pattern definition.

Validation, and a measurement flaw we corrected

We then ran both detectors, in their new default configuration, across fourteen open-source repositories. The corpus was 71,611 files. Total model API cost for the whole run was eleven cents, because in the new defaults the model is called only on the single judgment pattern, and that pattern is rare. The safe default turned out to also be the cheap one. For a tool that scans every pull request, that matters: the safe configuration carries no cost penalty that would tempt anyone to turn it off.

The run also taught us something we did not expect, and we are including it because leaving it out would be dishonest. We had planned to use the run to measure a false-positive rate against thresholds we had set earlier. The run found zero true positives across the whole corpus. Mature open-source projects do not commit real secrets, so there was nothing for a false-positive rate to be measured against. A false-positive rate needs a true-positive count in its denominator, and ours was zero, so the threshold we had written could not be evaluated. That was a flaw in how we designed the measurement, not in the detectors. We have dropped any false-positive-rate claim that depended on that run. A separate experiment, against a corpus with deliberately seeded and labelled secrets, is what will produce an honest precision number.

The safety property in this post does not depend on that arithmetic. It depends on the construction argument above: a detector that does not render model reasoning cannot leak through model reasoning, whether or not any real secret is present to leak.

How to check your own tooling

If you build or operate an LLM-based security tool, this is straightforward to check. Take a finding the tool produced on code that contains a secret or an internal identifier. Read the explanation text the tool shows to the user. Look for content copied out of the flagged code: a variable's value, a hardcoded string, an email address, an identifier. If that content is in the explanation, the tool has this exposure, and the next question for the vendor is what mitigates it.

If you buy these tools, the same question belongs on the due-diligence checklist: does the model's output ever quote our source content, including secrets, into a comment or a dashboard, and if so what removes it.
